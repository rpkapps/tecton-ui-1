Tecton UI carries the design system in **CSS variables**. `@tecton/react/globals.css`
declares a value for `--background`, `--primary`, `--ring` and the rest in `:root` and
`.dark`, exposes them to Tailwind, and the components read nothing else. Underneath, the
Tecton colour ramps replace Tailwind's stock palette (see [Palette](#palette)), so
`bg-red-140` in your own markup is a Tecton colour too.

You do not need to configure any of it. This page is for the cases where you want to
read a value, reuse one, or add a token of your own.

## Dark and light

Both modes come from the same design-system export: `--background` is the same reference
in `:root` and in `.dark`, and the token underneath switches value (`#f6f4f7` light,
`#1d1c1f` dark). Tecton applications are dark-first, so this site defaults to dark, but
light is equally complete.

Toggle the mode with the `dark` class on `<html>` (or `data-theme="dark"`, which the
tokens also honour). This site uses `next-themes`:

```tsx
<ThemeProvider attribute="class" defaultTheme="dark" enableSystem>
```

## Theme variables

Every variable below is available as a Tailwind utility (`bg-background`,
`text-muted-foreground`, `border-input`…). Prefer these over a literal colour: they
carry meaning, they follow the mode, and they move with the design system.

## Extra tokens

Tecton has semantics that the standard variables do not cover. They are declared the
same way and used by the Tecton variants and components:

| Token | Utilities | Used for |
| --- | --- | --- |
| `--success`, `--warning`, `--info`, `--neutral` | `text-success`, `border-warning`, `bg-info` | Status colour: text, borders and icons (readable on the page and card in both modes); with `--<status>-foreground` also a solid surface |
| `--success-surface`, `--warning-surface`, `--info-surface`, `--neutral-surface`, `--destructive-surface` | `bg-warning-surface`, `text-warning-surface-foreground` | Tecton's filled status surfaces (filled alerts, solid status badges); light mode keeps the pale yellow warning surface |
| `--destructive-foreground` | `text-destructive-foreground` | Text on a `destructive` surface |
| `--surface-alt` | `bg-surface-alt` | Alternate table rows |
| `--border-subtle`, `--border-strong` | `border-border-subtle`, `bg-border-strong` | Separator emphasis levels |
| `--font-sans`, `--font-mono` | `font-sans`, `font-mono` | Figtree / IBM Plex Mono |
| `--radius-sm` … `--radius-2xl` | `rounded-sm` … `rounded-2xl` | Tecton radius scale (2/4/8/12/16px) |

## Palette

Tecton's foundational colours are **contrast ramps**: fifteen families, each with
twenty-three steps from `50` (barely off the page background) to `1570` (maximum
contrast), and a separate set of values for light and dark mode. A step is the same
perceived distance from the background in both modes — `gray-120` is the pale grey of a
filled neutral badge on light and the deep grey of the same badge on dark — so one
utility class serves both modes and `dark:` variants are not needed.

The ramps are exposed to Tailwind as `--color-<family>-<step>`, so `bg-blue-560`,
`text-orchid-830`, `border-yellow-160`, `fill-green-560` and every other colour utility
work.

<Callout variant="warning" title="Tailwind's stock palette is removed">
  The stylesheet resets `--color-*: initial` before declaring the Tecton ramps, so
  `bg-red-500` or `text-zinc-400` produce **no CSS at all**. They type-check, they pass
  an ordinary lint, and they render unstyled — which is exactly what
  [`@tecton/eslint-config`](/docs/linting) exists to catch. Only `white` and `black` are
  kept (Tecton's own shades, for overlays such as `bg-black/10`).
</Callout>

<PaletteTable feedback="toast" />

Hover a cell for the utility name and both values. The semantic variables are literal
picks from these ramps, which gives a few recipes:

| Recipe | Classes | Where Tecton uses it |
| --- | --- | --- |
| Tinted surface with readable text | `bg-<family>-120 text-<family>-830` | Filled status badges and alerts |
| Solid fill with light text | `bg-<family>-560 text-<family>-50` | Filled status buttons, avatar badges |
| Coloured text or icon on the page | `text-<family>-560` (light) ≈ `text-<family>-460` | Status text, links |
| Border | `border-<family>-160` | Tinted alerts |

Reach for a palette step when no semantic token fits — a chart series, a tag colour, a
custom badge — instead of a hex value.

Not part of the palette on purpose: the `core` lightness scale, the `surface`,
`transparent`, `saturations` and `washes` sub-ramps (use the opacity modifier,
`bg-gray-370/20`, for translucency), the Matplotlib and Colorcet colormaps (chart
scales, not UI colours) and the app accent colours. The hot-pink focus outline is a
single value, not a ramp; it is `--ring`.

## What the variables do not carry

Colours, radii and fonts are variables. The rest of the Tecton look is built into the
components themselves, as variants rather than as CSS you have to apply:

- **Focus ring.** A solid 2px `#ff52a8` ring on every focusable control.
- **Hover and pressed colours.** Buttons lighten towards the foreground instead of
  darkening.
- **Flat controls.** No drop shadow on buttons, inputs and triggers.
- **Field surfaces.** The *outline*, *filled* and *text* variants of
  [Input](/docs/components/input), [Textarea](/docs/components/textarea) and
  [Select](/docs/components/select).
- **Status colours** and **divider emphasis** on [Alert](/docs/components/alert),
  [Badge](/docs/components/badge) and [Separator](/docs/components/separator).

Reproducing any of these with `className` is the one thing to avoid: the variant already
exists, and a hand-written copy stops following the design system.

## Adding your own tokens

An application-specific colour — a chart series, a status your product has and the
design system does not — is declared once as a variable and exposed to Tailwind:

```css title="src/styles/app.css"
@import "@tecton/react/globals.css";

:root {
  --highlight: var(--tecton-palette-yellow-830);
}
@theme inline {
  --color-highlight: var(--highlight);
}
```

Pick the value from the palette rather than typing a hex code: the palette variable
already switches with the mode, so one declaration covers dark and light. A colour the
palette genuinely does not cover is a change to the design system — raise it rather than
inventing one locally, where it has no dark pair and has passed no contrast check.

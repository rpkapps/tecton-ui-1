---
title: Portal Provider
description: "Chooses the element that Tecton overlays portal into. For pages that render several isolated React roots."
---

## Usage

```tsx
import { PortalProvider } from "@tecton/react/tecton/portal"
```

```tsx
<PortalProvider container={overlayRoot}>
  <App />
</PortalProvider>
```

Every Tecton overlay — `Dialog`, `Sheet`, `Popover`, `Tooltip`, `Select`, `Combobox`, `DropdownMenu`, `CommandDialog` — portals into `document.body` by default. `PortalProvider` changes that target for its whole subtree without any prop on the overlays themselves.

## When to use it

Applications that render **several isolated React roots on one page** (micro frontends, embedded widgets) give each root a body-level container of its own. The overlays still escape any `overflow: hidden` ancestor, while the container carries that root's scope class, mode class and ownership attributes, so the styles compiled for that root still reach its overlays:

```tsx
const overlayRoot = document.createElement("div")
overlayRoot.setAttribute("data-mfe", "asset-tracker")
document.body.append(overlayRoot)

createRoot(mountNode).render(
  <PortalProvider container={overlayRoot}>
    <AssetTracker />
  </PortalProvider>
)
```

A single-root application does not need it.

## Notes

- The provider owns a Tecton container context. Each overlay passes its resolved target directly to its React Aria Components primitive, so isolated React roots do not depend on sharing React Aria's private context.
- With no provider, or with `container={null}`, overlays pass no container at all and React Aria applies its own default (`document.body`, once hydration is over).
- A submenu is the exception: React Aria mounts it inside the root popover's container, which is already in the provider's container. Overriding that would detach the submenu from its parent menu, so Tecton leaves it to React Aria.
- `Drawer` is built on Base UI, which has no portal context of its own, but it reads this one and forwards the resolved container to its Base UI portal, so it lands in the same place as the other overlays.
- `container={null}` clears an outer provider and restores the default.
- [`ThemeRoot`](/docs/tecton/theme-root) is the recommended way to get a container: it creates one body-level element that mirrors the root's classes, marks it with `data-tecton-root` and wires it to this provider, so an independently deployed application does not have to manage the element itself.

## API Reference

### PortalProvider

| Prop        | Type                                                 | Default | Description                                                                                            |
| ----------- | ---------------------------------------------------- | ------- | ------------------------------------------------------------------------------------------------------ |
| `container` | `HTMLElement \| null \| (() => HTMLElement \| null)` | -       | Element the overlays portal into. A function is called while each overlay renders. `null` restores `document.body`. |
| `children`  | `ReactNode`                                          | -       | Subtree whose overlays are redirected.                                                                 |

### usePortalContainer

`usePortalContainer(): HTMLElement | null` — the current portal container, or `null` when React Aria will use `document.body`.

### usePortalTarget

`usePortalTarget(): HTMLElement | undefined` — what the overlays hand to their React Aria primitive: the container, or `undefined` to let React Aria resolve the target itself. Tecton's own overlays call it; applications use `PortalProvider`.

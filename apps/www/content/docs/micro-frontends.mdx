---
title: Micro-frontends
description: Run several independently deployed applications, each with its own copy of @tecton/react, in one document — scoped utilities, inherited shell variables, one overlay container per root, and the shared modules they must agree on.
---

A remote is an application built and deployed on its own and mounted into a Tecton shell (a Module Federation remote, an embedded widget). It brings its own `@tecton/react`, possibly another version than the shell's, so it compiles its utilities into a CSS `@scope` around its own root. The shell needs nothing beyond its usual `globals.css`: it owns the document, the fonts and the theme, and its variables inherit into every remote.

## Set up a remote

<Steps>

<Step>Render `ThemeRoot` around the mounted tree</Step>

Pick one scope class per deployable and use it as the React root's `identifierPrefix` too, so two roots never generate the same ids.

```tsx title="src/mount.tsx"
import { createRoot } from "react-dom/client"
import { ThemeRoot } from "@tecton/react/tecton/theme-root"

import "./styles/remote.css"

export function mount(element: HTMLElement, props: MountProps) {
  const root = createRoot(element, { identifierPrefix: "mfe-a" })
  root.render(
    <ThemeRoot className="mfe-a">
      <App {...props} />
    </ThemeRoot>
  )
  return () => root.unmount()
}
```

[`ThemeRoot`](/docs/tecton/theme-root) marks its element with `data-tecton-root` (what the scoped stylesheet keys on) and creates one body-level container with the same classes for the remote's overlays. It is also the remote's [`TectonProvider`](/docs/tecton/provider): pass `dir` and `locale` for another language or direction, and nest a `TectonProvider` with `navigate` when the remote has its own router.

<Step>Write the stylesheet entry</Step>

Tailwind's theme and utilities, then `scoped.css`: utilities only, no variables, no preflight, no fonts. Importing all of `tailwindcss` would reset the shell's document.

```css title="src/styles/remote.css"
@layer theme, base, components, utilities;
@import "tailwindcss/theme.css" layer(theme);
@import "tailwindcss/utilities.css" layer(utilities);
@import "@tecton/react/styles/scoped.css";
@source "./src/**/*.{ts,tsx}";
```

<Step>Scope the output</Step>

Run the plugin after `@tailwindcss/postcss` with the same scope class. It wraps the sheet in `@scope (.mfe-a) to ([data-tecton-root])`, so the remote's utilities win on the remote's elements whatever order the stylesheets load in.

```js title="postcss.config.mjs"
import tailwindcss from "@tailwindcss/postcss"

import scopeTecton from "@tecton/react/postcss/scope"

export default { plugins: [tailwindcss(), scopeTecton({ scope: ".mfe-a" })] }
```

<Step>Share the modules the applications must agree on</Step>

`@tecton/react/federation/shared` is that list as data: `@tecton/react/` as a prefix share, `react`, `react-dom`, `sonner`, Tecton's internal libraries and `recharts` (never eager). None is a singleton, since the applications release on their own schedules. It carries no versions: take `requiredVersion` from the application's own dependencies (Tecton's internal libraries get theirs from `@tecton/react`'s package.json). Pin `react` and `react-dom` to the same exact version in every application.

```js title="rspack.config.mjs"
import { dependencies } from "./package.json" with { type: "json" }
import { shared } from "@tecton/react/federation/shared"

const requiredVersion = (name) => dependencies[name.replace(/\/$/, "")]

new ModuleFederationPlugin({
  shared: Object.fromEntries(
    Object.entries(shared).map(([name, policy]) => [
      name,
      { ...policy, requiredVersion: requiredVersion(name) },
    ])
  ),
})
```

<Step>Leave the toasts to the host</Step>

Sonner's queue is module state and a remote may load its own `sonner`, so its `toast` could land in a queue no `Toaster` renders. The host mounts the one `Toaster` and passes its `toast` in the mount props; the remote calls that, with text rather than React elements.

```tsx
// host
import { toast } from "sonner"

mount(element, { toast })

// remote
props.toast.success("Simulation finished")
```

</Steps>

## Plugin options

| Option | Default | What it does |
| --- | --- | --- |
| `scope` | required | Selector of the remote root: the class on `ThemeRoot`. |
| `boundary` | `"[data-tecton-root]"` | Lower limit (`@scope (…) to (…)`): the scope ends at the next Tecton root, so a remote mounted inside this one keeps its own styles. A selector, or `false` for none. A root matching its own boundary is not excluded. |
| `rootRules` | `"scope"` | Rewrites a leading `:root` / `html` / `body` to `:scope`; `"document"` leaves those rules unscoped. |
| `keyframes` | derived from `scope` | Renames the sheet's `@keyframes` to `<name>--<suffix>`; `{ suffix }` sets the suffix, `false` keeps the names. |

## Theme

A remote declares no theme variables: the shell's variables, palette, radii, tenant customisations and mode inherit into the subtree and its overlay container. If the shell is too old to know a variable, the remote's utilities fall back to the raw Tecton token, then to a `light-dark()` literal that follows the shell's `color-scheme`.

`theme="dark"` or `theme="light"` on `ThemeRoot` pins the remote to one mode (a map viewer that stays dark in a light shell), overlays included. See [inverted sections](/docs/theming#inverted-sections).

A remote with no Tecton shell (a demo, a test harness, an embed elsewhere) or with its own token set adds the theme and the fonts itself; leave `scoped-theme.css` out whenever there is a shell, since it stops the remote following it:

```css title="src/styles/remote.css"
@import "@tecton/react/styles/scoped.css";
@import "@tecton/react/styles/scoped-theme.css";
@import "@fontsource/figtree/400.css";
@import "@fontsource/figtree/500.css";
@import "@fontsource/ibm-plex-mono/400.css";
@import "@fontsource/ibm-plex-mono/500.css";
```

## Sidebars

Give each application's `SidebarProvider` its own `cookieName` (or `false`), so they do not share one cookie. The sidebar registers no keyboard shortcut, so no key press toggles them all. See [Sidebar](/docs/components/sidebar#several-sidebars-in-one-document).

## Limits

- **Browser floor.** `@scope` needs Chrome/Edge 118+, Safari 17.4+, Firefox 146+, with no polyfill; older browsers get the unscoped cascade, so keep one Tecton version for them.
- **`@property` and `@font-face` are last-definition-wins.** They cannot be scoped; the names are stable, so only the values of two versions can differ.
- **DOM-shape selectors cross versions.** Variants that match structure (`in-data-[slot=button-group]`, `has-data-[slot=…]`, `peer-data-*`) reach markup of another copy: do not nest one application's components inside another's compound component.
- **A remote's overlay inside a host modal** counts as outside it: the host pulls focus back and closes on the first click. Let one side own the whole modal flow.

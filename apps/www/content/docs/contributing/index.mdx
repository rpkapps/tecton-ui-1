<Callout title="This section is for people who work on Tecton UI">
  Everything here describes how the library is *produced*: the upstream project it is
  generated from, the registry mirror, the token pipeline and the docs sync. If you are
  building an application **with** Tecton UI, you never need any of it — start at
  [Installation](/docs/installation) instead.
</Callout>

Tecton UI is not hand-written. Every standard component is generated by the
[shadcn](https://ui.shadcn.com) CLI from the **React Aria** base, using a Tecton
**style** (`aria-tecton`) that is authored exactly like upstream's own presets. The
Tecton visual language is applied through the theme variables and that style — never
through overrides of the generated files — which is what keeps a component update a
single command.

## The rule that explains the rest

> No generated file is ever edited by hand.

`packages/tecton-react/src/components/**`, `src/hooks/**`, `src/lib/**` and the
structure of `src/styles/globals.css` come out of the CLI. `pnpm generated:check` diffs
every item against the registry and fails on any drift. Whenever you want to change how
a generated component looks, you change its *input* — the style overlay, the token map —
and regenerate.

## Repository map

| Path | What lives there |
| --- | --- |
| `packages/tecton-react` | The published surface: `components/`, `tecton/`, `icons/`, `blocks/`, `styles/` |
| `packages/eslint-config-tecton` | `@tecton/eslint-config` — the consumer guardrails |
| `apps/www` | This documentation site, the block registry host and the theme playground |
| `scripts/registry-mirror/overlay` | `style-tecton.css` and `tecton.patch` — the `aria-tecton` style |
| `packages/tecton-react/tokens` | The Tecton token export and the map onto the theme variables |
| `docs/` | `UPSTREAM.md` (pinned commit), `TOKEN-MAPPING.md` (generated), `OVERFLOW-RULES.md` |

## The four pipelines

| Pipeline | Input | Command | Page |
| --- | --- | --- | --- |
| Components | `scripts/registry-mirror/overlay/` | `shadcn add <item> --overwrite` | [Components](/docs/contributing/components) |
| Theme | `tokens/tecton.map.json`, `tokens/tecton.tokens.json` | `pnpm tokens:build` | [Tokens & theme](/docs/contributing/tokens) |
| Icons | `packages/tecton-react/icons-src/tecton/` | `pnpm --filter @tecton/react icons:build` | [Icons](/docs/contributing/icons) |
| Docs | upstream docs + `apps/www/scripts/docs-extras/` | `pnpm docs:sync` | [Docs site](/docs/contributing/docs-site) |

## Where new code goes

<Steps>

<Step>A Tecton look for a component that already exists</Step>

Add a **variant** through the style overlay. Never a second component, never a
`className` recipe in the docs, never a `.style-*` or `[data-slot]` override. See
[Components](/docs/contributing/components#changing-the-tecton-style).

<Step>Behaviour upstream has no component for</Step>

A Tecton component in `packages/tecton-react/src/tecton/`. Follow the generated
components' conventions: `data-slot` attributes, `cva` for variants, `cn` from `"cn"`,
React Aria primitives, `onPress` rather than `onClick`.

<Step>A composition made of existing components</Step>

A **block** in `packages/tecton-react/src/blocks/`. Blocks are the only items published
to the `@tecton` registry; `registry:build` fails if anything else reaches
`registry.json`.

</Steps>

## Before you push

```bash
pnpm generated:check   # no generated file was hand-edited
pnpm tokens:check      # mapping complete, contrast holds
pnpm lint && pnpm typecheck && pnpm test
pnpm --filter @tecton/eslint-config test   # if you touched the guardrails
```

## Writing for two audiences

The documentation is split by reader, and the split is the point:

- **`/docs/*`** is written for application developers. It never mentions shadcn, React
  Aria, the registry mirror or the generated-file pipeline — from an application's side
  those are implementation details it cannot see and must not depend on. Components are
  Tecton components; the variables are Tecton theme variables.
- **`/docs/contributing/*`** — this section — is where the machinery is named and
  explained.

When you add a page, pick the audience first. If a sentence only makes sense to someone
with the monorepo checked out, it belongs here.
